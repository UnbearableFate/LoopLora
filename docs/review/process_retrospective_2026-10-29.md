# LoopLora 探索过程复盘，以及对 research-agent 的改进建议（2026-10-29）

写于 2026-10-29 17:24 JST。写的时候 LSQT 的 U 对照组（作业 3725694）还在跑。本文把 LoopLora 这三天的实际做法和 `/work/xg24i002/x10041/research-agent`（research-tree 插件 0.2.0，config v3，schema 23）的设计放在一起比较，找出能改进 research-agent 的地方。

数据来源与口径见附录 A。research-agent 部分依据只读调研（引用了文件行号，关键条目已抽查），原文件为 `scratchpad/research_agent_survey.md`，本文第 8 节列出所用条目。

## 0. 结论

**LoopLora 做对的几件事：**
- 用文档、git 和小脚本搭了一个轻量流程：预注册、发布、批准、审计、合并、全量测试。三天里在真实的 PBS 集群上完成了 27 项预注册研究、542 个作业、113 node·h，论文 64 页。
- 10-29 下午的批次最能说明问题：13:00 用户批准 G1–G4，到 16:05，G1–G5 都完成了预注册、实现、测试、正式实验、审计和合并，论文也随之更新；只剩 U 对照组还在跑。

**LoopLora 最大的成本不在算力，在 token。**
- 统计范围内 Claude 侧的输入约 17.4 亿 token，几乎都是缓存读取；Codex 侧约 5.0 亿。
- 每次调用平均带约 20 万 token 的上下文，其中启动时只有约 3.1 万，其余是工具输出累积起来的。
- 长寿命 worker 反复压缩上下文：sn-sym 19 次，sn-llm 11 次，主会话 14 次。
- Codex 的周额度在项目中途成为硬约束，按用户规则把全部角色换成了 Sonnet 子代理。

**research-agent 的规则设计比 LoopLora 严格、可审计，但三处有缺口：**
- 没有真实 HPC/PBS 运行的证据，也没有调度器实现，只有对站点技能的文字约定。
- 没有 token 计量和预算。
- 模型或额度不可用时没有预案。阶段评审因 Fable 不可用而全部 BLOCKED；S1 场景因账户额度用完而中断。

LoopLora 正好在这三处有可用的实践和数据。

**建议的优先次序（第 9 节详述）：**
1. 做一个 PBS 站点适配器，并做一次真实集群验收。
2. 加 token 计量，并给长寿命 worker 定轮换规则。
3. 让用户在立项时预先授权模型和宿主的替补顺序。
4. 预注册中写明"结果区间对应的下一步"，并支持研究线级的止损。
5. 在正式运行前加一道发布门：按冒烟实测冻结步数和 walltime，做配置哈希和重载一致性检查，再记录批准。

## 2. 效率

### 2.1 时间花在哪里
- **排队几乎不花时间**。排队等待的中位数是 0.01 h，p90 是 0.11 h。例外是维护期：3 个 P1-L 作业排了 39–40 h，13 个作业从未启动，合计排队 5.1 h。
- **作业很碎**。debug-g 上 251 个作业，运行时间中位数约 1 分钟；regular-g 上 290 个，中位数约 9 分钟。全部作业的运行时间 p90 是 0.76 h。
- **walltime 申请偏大**。实际用量占申请量的中位数是 0.17，node·h 上申请量约为实用量的 2.15 倍。这次队列空，没有造成损失；队列拥挤时会影响回填。
- **非零退出 39 个**。其中 33 个是退出码 1，大多是测试和冒烟作业，也就是在正式实验之前就发现了缺陷，例如 `torch.sqrt` 用在 Python float 上、测试期望值写错。
- **GPU 利用率 60.8%**。这是 PBS 记录的数，只覆盖每个作业最后约一小时，仅作参考。

### 2.2 加速的因素
1. **并行的长寿命 worker，各有 worktree**。sn-llm、sn-p1l、sn-oracle、sn-core、sn-paper 同时推进不同研究，彼此不改对方的文件。
2. **流程模板可以复用**。DPFP 的发布流程是：冒烟计时 → 冻结步数 → 计算配置哈希 → 重载检查 → 批准。DPFP-X、SQ2、LSQT、LSQT-U 都沿用了它。U 对照组从批准准备（15:51）到正式实验提交（16:05）只用了约 15 分钟。
3. **预注册里事先写好判定规则和结果区间**。结果一出来就能机械地给出结论，不需要再讨论。
4. **测试一律在计算节点上跑，并在正式实验前跑**。缺陷在 1–5 分钟的测试作业里暴露，没有出现正式实验跑到一半才失败的情况。

### 2.3 拖慢的因素
1. **编排者是串行瓶颈**。所有预注册、发布、合并和论文改动都经过主会话审核。审核确实拦下了问题：论文里的因果措辞、对 W3 的错误称呼、测试期望值、队列选错。但同一时刻只能审一件事。
2. **等待要中转**。worker 交回 `WAIT <ids>`，编排者布置一个监视任务，作业结束后再发消息唤醒 worker。每次中转要在主会话里花一到两次调用，每次带约 21 万 token 的上下文。
3. **早期用 20 分钟定时轮询检查 worker**，用户指出后取消。
4. **几次运维失误**：
   - 超过 30 分钟的作业误投 debug-g；
   - `--commit HEAD` 在主 checkout 里解析成了错误的提交（作业 3724073/74 已删除）；
   - 代码里写死了一个截止时间，在维护后会触发，等于一颗定时炸弹（3a7f111 已修）；
   - 同一批作业布置了两个监视任务。

## 3. Token 使用

### 3.1 总量

| 主体 | 模型 | 调用次数 | 输入（含缓存读写） | 输出 |
| --- | --- | ---: | ---: | ---: |
| 编排者（主会话） | Opus 5.5 | 2,158 | 4.60 亿（缓存读 4.55 亿） | 182 万 |
| 长寿命 worker（6 个） | Sonnet 5.5 | 4,596 | 约 9.7 亿（缓存读 9.29 亿） | 207 万 |
| 一次性评审和杂项子代理（16 个） | Sonnet 5.5（15 个）/ Opus 5.5（1 个） | 约 1,650 | 约 3.0 亿 | 约 37 万 |
| 外部评审 rv-fable（2 次） | Fable 5.1 | 38 | 699 万 | 29 万 |
| 早期 Codex worker（31 个会话，10-26 18:49–10-27 07:27） | GPT-6.1-sol | — | 4.70 亿（缓存 4.59 亿） | 271 万（其中推理 121 万） |
| 外部评审 rv-astra（4 个会话） | GPT-6-Astra | — | 3,166 万 | 17 万 |

按 worker 看缓存读取：

| worker | 缓存读取 | 调用次数 | 压缩次数 |
| --- | ---: | ---: | ---: |
| sn-sym | 3.75 亿 | 1,848 | 19 |
| sn-llm | 2.03 亿 | 1,024 | 11 |
| sn-oracle | 1.26 亿 | 640 | 7 |

| sn-p1l | 0.83 亿 | 409 | 4 |

13 个代码评审子代理合计约 2.63 亿，约占子代理总量的五分之一。

### 3.2 规律
- **输入量约等于调用次数乘以平均上下文**。各 agent 的平均上下文大多在 17–23 万 token 之间（最低的约 13 万），最大约 36.7 万，到这里就压缩。每个子代理第一次调用时只有约 3.1 万 token（系统提示、工具和技能列表）。所以八成以上的上下文是工作中读进来的文件、日志和测试输出。
- **一次性评审子代理也很贵**。它们只活 100 次左右的调用，平均上下文却也有 17 万上下。原因是评审要读整段差异和相关代码，读进来就一直留着。
- **输出量很小**，只占输入的约 0.3%。费用主要由上下文长度和调用次数决定，不由写了多少决定。
- **压缩频繁，但没有丢状态**。每项工作的状态都写在文件里（`WP-*-state.md`、报告、`docs/workers.md`），压缩后从文档恢复。这是"以文档为基础交流"带来的直接好处。
- **Codex 的额度是硬约束**。前 12.6 小时用掉约 4.7 亿输入 token，用户随即定下规则：周额度低于 20% 时交接。10-27 07:27 全部 7 个 Codex worker 交接给 Sonnet 子代理，角色、worktree 和状态文档原样保留，交接没有丢失工作。

### 3.3 教训
1. 应当按角色记录 token 用量并设预警阈值，像 node·h 一样对待。这次的数字是事后从会话记录里算出来的。
2. 长寿命 worker 的价值在于积累了代码库知识，代价是每次调用都要重读巨大的上下文。值得在任务边界主动开新会话、从状态文档续接，而不是等到上下文满了被动压缩。这一点本次没有做，是推断，需要实测验证。
3. 评审的花费可以靠收窄范围来控制。给评审一份清单，写明差异范围、要核对的不变量和文件路径。比起"审一下这个分支"，它读的东西少得多。

## 4. 多 agent 管理

### 4.1 结构
- **编排者**：Opus 5.5 主会话。它负责预注册审核、发布批准、合并、全量测试、计划文档和对用户的汇报。
- **固定角色的 worker**：先用 7 个 Codex worker，开在 herdr 标签页里；10-27 起换成 Sonnet 子代理（sn-p1l、sn-llm、sn-oracle、sn-sym、sn-paper，10-29 新增 sn-core）。每个 worker 对应一条分支和一个 worktree，用 SendMessage 续接，上下文保持不变。
- **一次性评审**：正式计算前的只读静态评审，例如 rev-tsm、rev-release、rev-rfxlsq。worker 也可以自己开评审子代理，嵌套深度为 2。
- **外部评审**：Claude Fable 5.1 和 Codex GPT-6-Astra 各两轮，开在 herdr 新标签里，拿到简报后检索文献、提出改进。第二轮的建议被整理成候选研究 G1–G10，用户批准其中 G1–G5。
- **交流方式**：任务书 `docs/tasks/*.md` 加一条短消息。worker 回复的最后一行用固定格式：`WAIT <作业号> | <下一步>` 或 `STOP: <原因>`（`docs/tasks/_common_rules.md`）。登记表在 `docs/workers.md`，事件日志在 `scratchpad/agents.txt`。

### 4.2 有效的做法
- **WAIT/STOP 协议**。worker 不轮询；编排者对每个 WAIT 只布置一个监视任务；STOP 表示需要编排者决定，例如锁定、偏离预注册、超出资源上限。
- **正式计算前的静态评审**。rev-tsm 发现 1 个 Medium 级问题（第一次评测没有和训练哈希比对），rev-release 发现平局规则会在 2–10% 的情况下触发冒烟检查。两者都在正式运行前修好了。每次评审约 0.08–0.57 亿 token，比在 GPU 上跑出错误结果便宜。
- **交接不丢工作**。Codex 换成 Sonnet、多次压缩，都靠状态文档无损续接。
- **跨模型族的外部评审**。两家评审独立给出的建议有相当部分重合（`plan/followup_2026-10-29.md` §1），重合的部分可信度更高。

### 4.3 问题
- **编排者审核集中**，是吞吐上限（见 2.3）。
- **事件日志放在 scratchpad**（`/tmp/...`），会话结束就没了，不是持久记录。research-agent 的消息 JSONL 在这一点上更好。
- **`docs/workers.md` 的状态栏越写越长**，单格超过 1,000 字，已经难以阅读。状态应当结构化存放，文档里只留指针。
- **曾对会话内的子代理做 20 分钟定时轮询**。子代理结束时本来就会通知，轮询是多余的。

## 5. 研究分支管理

### 5.1 研究线
- **计划文档承认自己不是权威**。它持续更新 E.2（对原计划的调整及理由）和 E.3（任务状态）。新的分析写成 `plan/followup_*.md`，候选按每 node·h 的预期价值排序，成批交给用户批准。
- **预注册包含这些部分**：
  - 结果出来之前写定的判定规则；
  - 登记的预测（只报告，不参与判定）；
  - 相对任务书的偏离清单；
  - 预算表；
  - blake2b 摘要。
- **修订用 Clarification**。在读取相关数据之前提交 C1，例如 LSR、CTC、SQ2 各有一份，带新的摘要。
- **结果区间各有后果**。以 LSQT 为例：≥ 48.5% 触发 W3；40% 到 < 48.5% 既不触发也不关闭；< 40% 证伪并关闭这条线。条件对照也可以写进预注册，例如 U 对照组只在最好的臂 ≥ 40% 时才跑。
- **研究线级的止损**。学习式写入器线在 DPFP 之后按登记规则停止。之后每次重开，包括 DPFP-X、SQ2 和 LSQT，都要用户批准并单独预注册。
- **测试区段统一分配**。各研究的测试区段不相交，记在 `CONFIRMATION_WINDOWS` 里，例如 LSR 用 [106000,108000)，B8W 用 [108000,110000)，由测试逐条断言。

### 5.2 git 分支
- 每个角色一条长期分支加一个 worktree；只有编排者能合并到 master，合并前先审核；合并后在计算节点上对明确的提交哈希跑全量测试。从不 push。
- **冲突集中在共享注册表**，例如 `CONFIRMATION_WINDOWS` 和它的测试。改成"逐条断言"后，各研究新增条目时就不会互相冲突。
- **合并顺序需要事先规划**。例如 wp/llm 和 wp/oracle 都改到 P1-L 的代码路径，所以等 wp/p1l 合并之后才合并它们。

### 5.3 教训
- **"开放"区间要附带默认行动**。LSQT 落在开放区间，按登记规则这条线"保持开放"，但没有写开放之后默认做什么。这会让研究线无限期挂着。
- **验证集被反复使用**。D128-3 是在验证集上选出来的，SQ2 和 LSQT 又用同一个验证集判定。每份报告都注明了这一点，但最好在流程层面记账：一个验证集已经被多少次选择用过。

## 6. 作业管理

| 组成 | 做法 |
| --- | --- |
| 提交 | `scripts/submit.py`（只用标准库）：检查用户上限（每个作业 ≤ 8 节点 × 1 h；带 `--scale-up <prereg>` 时 ≤ 2 h）；`--commit <完整哈希>` 绑定代码快照；每个作业写一份规格 JSON 和日志，以及 `.started`、`.exit` 标记 |
| 尺寸 | walltime 等于冒烟实测乘 1.5，向上取整；发布文件冻结步数、评测点、配置哈希、预注册摘要和 walltime |
| 正式运行门 | 发布文件 → 重载检查（配置一致、重载结果一致、预测零差异）→ 编排者提交 `approval.json` → 提交正式作业 |
| 等待 | worker 交回 WAIT；编排者在后台跑 `wait_jobs.sh`，每 120 s 查一次 `qstat -H`；作业结束时通知编排者，编排者再唤醒 worker |
| 验收 | 退出码 0 不算成功。还要核对步数、评测点、NaN/inf、配置哈希和提交哈希；审计时把记忆清零或打乱，确认答案确实来自记忆 |
| 维护期 | 写恢复 runbook（`docs/tasks/resume_2026-10-28.md`），用队列状态监视任务唤醒 |
| 并发 | 项目上限是 16 个运行中作业，worker 平分配额（每人 ≤ 6，后来 sn-llm 提到 8） |

**教训**：
- 队列规则要在工具里强制执行，不要靠记忆。例如提交时自动检查"debug-g 上限 30 分钟"。
- `--commit` 只接受完整哈希。不要让它去解析 `HEAD`，因为不同 worktree 里的 HEAD 不同。
- 测试代码里不能写死日期。
- 每个作业的 node·h 要写进报告的成本表。这次每份报告都写了，汇总成本可以直接核对。

## 7. 主要事故与教训

| 事故 | 后果 | 处理 | 推广到流程的规则 |
| --- | --- | --- | --- |
| Codex 周额度将尽 | 12.6 h 用掉 4.7 亿 token | 按用户规则把全部角色交接给 Sonnet 子代理 | 立项时由用户预授权替补顺序和触发阈值 |
| 误解预算口径（"单个实验"） | 规划过紧，用户纠正 | 改为每个作业设上限，总量不封顶 | 立项时逐项确认每个上限的单位和作用范围 |
| 比较范围过宽（要求胜过更大 rank） | 用户指出不必要 | 改为只做同 rank 比较 | 证据要求由用户确认，不由编排者自行加码 |
| 20 分钟定时轮询子代理 | 浪费主会话 token | 改为事件驱动 | 会话内子代理不轮询 |
| debug-g 投了超过 30 分钟的作业 | 需要重新提交 | 改投 regular-g | 提交工具检查队列上限 |
| `--commit HEAD` 解析错误 | 删掉 2 个作业 | 一律用完整哈希 | 拒绝符号引用 |
| 代码里写死截止时间 | 维护后测试会失败 | 删除 | 静态检查禁止日期常量 |
| 监视任务重复 | 消息重复 | 停掉多余的那个 | 布置前先查有没有同样的监视任务 |
| 论文出现因果性过度表述 | 审核发现，未合并 | 改成"与……一致，未检验" | 维护"不可写的表述"清单，并在审核时检查 |
| 时间戳写错（14:30 应为 14:27） | 文档与事实不符 | 修正后改写未推送的提交 | 写时间戳前先跑 `date` |
| 测试期望值写错（5.7 对 5.657） | 测试失败 | 改正期望值，断言不放宽 | 先查清原因再改测试 |

## 8. 与 research-agent 对比

research-agent 的设计要点，括号内是调研文件引用的出处：
- **角色**：Leader（主会话）、Explorer、Architect、每个节点一个 Worker、Analyst、按需 UI，以及只能通过封装调用的 Reviewer（RULES:11-23）。
- **数据与文档**：LatticeDB 只存索引、状态和关系，正文写在不可变文档里（DOCLIB:3-12）。
- **筛选与确认**：廉价筛选不做逐次代码评审；要判 GO，必须在从未用过的材料上独立确认，并通过跨模型族的五维评审（RULES:161-166）。
- **作业账本**：预留 → 认领 → 提交 → 挂接 → 结算；状态未知的作业不重新提交（DB:2044-2290）。
- **调度器**：没有调度器代码，只有对站点技能的五条最低义务（CFG:7-20）。
- **验证范围**：没有在 GPU 或 PBS 上跑过真实研究（README:343）。阶段评审因 Fable 不可用全部 BLOCKED（AGENTS-README:18-19）。

| 维度 | LoopLora（实践） | research-agent（设计） | 对比结论 |
| --- | --- | --- | --- |
| 状态存储 | markdown、git 和 JSON 记录；状态写在长表格里 | 图数据库只存状态和关系，正文写在不可变文档里 | research-agent 更好；LoopLora 的状态表已经难读 |
| 交流 | 任务书加短消息；WAIT/STOP 行协议；事件日志不持久 | 消息 ≤ 1000 字节、正文 ≤ 200 字、最多引用 5 份文档；按角色写 JSONL 日志；"不盲目重发" | 理念相同；research-agent 有持久日志，LoopLora 有机器可读的等待协议 |
| 计算预算 | 每个作业设上限（提交工具强制）；每份预注册列 node·h 预算表；报告记录实际用量 | 每个 run 设上限；按预算池记账；超出预估倍数时提醒；超出预留时暂停准入 | research-agent 更完整；LoopLora 的预算由用户逐研究批准，同样可行 |
| token 预算 | 无，事后统计 | 无，只管评审花费（USD） | **两边都缺** |
| 模型或额度不可用 | 用户规则：Codex 额度低于 20% 时交接；交接无损 | 不可用就报告并 BLOCKED，不悄悄替换模型 | research-agent 缺少预授权的替补方案 |
| worker 粒度 | 按领域的长寿命 worker，连续做多项研究 | 每个假说节点绑定一个 worker | 各有利弊，见建议 6 |
| 评审 | 正式计算前静态评审（同模型族，便宜）；编排者审核每次合并；外部跨模型族评审 | 封装调用的跨模型族评审：新会话、只给路径、工单制、可申诉；廉价筛选不评审 | research-agent 更规范；LoopLora 的数据说明计算前评审划算 |
| 预注册 | 判定规则、结果区间及其后果、条件对照、Clarification、摘要 | 冻结 `screening_contract` 的五个字段和 `minimum_practical_gain`；结论三态由计算得出 | LoopLora 能表达更细的后果；research-agent 的固化更强 |
| 确认材料 | 各研究的测试区段不相交，测试逐条断言 | 项目级材料使用账本，禁止复用 | 等价；research-agent 由代码强制执行 |
| 发布门 | 按冒烟实测冻结步数和 walltime，算配置哈希，做重载检查，记录批准 | 先跑 sanity；`method_spec` 固定方法身份；walltime 不属于方法身份 | research-agent 没有"调度冻结"和"重载一致性"这一步 |
| 调度器 | `submit.py`、`job.pbs`、监视任务；542 个真实作业 | 文字约定加站点技能；没有真实运行 | **research-agent 缺一个真实的 HPC 适配器** |
| 等待 | 每个 WAIT 一个监视任务，不轮询 | 先做独立工作；监视真正的依赖；不重复布置监视；唤醒后只核对，不做判定（RULES:196-205） | 规则一致；research-agent 的规则写得更全 |
| 合并与集成 | 编排者合并；在计算节点上对明确哈希跑全量测试；冲突靠逐条断言化解 | 分支生命周期记在 DB；删除前打 `exp/<id>` 标签 | research-agent 没有"合并后全量测试"这道门 |
| 对外表述 | 论文证据台账、"不可写的表述"清单、`check_paper_tex.py` 数字检查 | `evidence.py` 检查数字精确出现在引用文件里；`CLAIM_EXCEEDS_EVAL_TYPE` | LoopLora 的措辞约束覆盖面更广 |
| 防止反复试错 | 研究线止损；重开要用户批准并重新预注册 | 探索份额、同方向修复上限、停滞计数、失败预算 | research-agent 更系统；LoopLora 有研究线这一层 |

## 9. 对 research-agent 的改进建议

按预期收益排序。每条写明问题、LoopLora 的证据、建议和代价。

### 建议 1：PBS 站点适配器和一次真实集群验收（最高优先）
- **问题**：
  - 插件里没有调度器代码，只要求站点技能履行五条义务（CFG:13-19）。
  - 现行 v3 合同没有在 GPU 或集群上做过端到端验收（README:343）。
  - 真实运行中，站点技能名都写错过（RRE #4）。
- **LoopLora 的证据**：在 Miyabi 上跑了 542 个作业。出过的问题都在提交和等待环节：
  - 队列上限没检查；
  - `HEAD` 解析错误；
  - 监视任务重复；
  - 维护期需要恢复手册。
- **建议**：发布一个参考站点技能，例如 `miyabi-research-tree`，把五条义务做成代码：
  1. 实现 `reserve_submission` → `qsub` → `attach_job` → `settle_reservation`。用量来自 `qstat -H -f` 的 `resources_used`。
  2. 只接受完整提交哈希，并在 git worktree 里检出那个提交来运行。
  3. 检查队列路由（debug-g ≤ 30 min，其余走 regular-g），并检查节点数 × walltime 不超过单个 run 的上限。
  4. 每个作业写规格 JSON 和 `.started`/`.exit` 标记，供 `reconcile_submission` 按 `submission_key` 找回作业。
  5. 每个依赖布置一个监视任务，作业结束时唤醒 Leader；查询失败时状态保持 unknown。
- **代价**：中等。可以直接改写 LoopLora 的 `scripts/submit.py`、`scripts/pbs/job.pbs`、`wait_jobs.sh` 和 miyabi 技能。验收时用一个约 5 node·h 的小真实项目。

### 建议 2：token 计量，以及长寿命 worker 的轮换规则
- **问题**：research-agent 没有 token 计量和预算（只管评审 USD）。
- **LoopLora 的证据**：
  - 本次 Claude 侧约 17.4 亿输入 token，Codex 侧约 5.0 亿。
  - 每次调用平均带约 20 万 token 上下文，启动时只有 3.1 万。
  - sn-sym 压缩了 19 次，主会话 14 次。
  - Codex 的额度在第 13 个小时就成了约束。
- **建议**：
  1. 增加 `usage_ledger`，按角色和节点汇总调用次数、缓存读写和输出。数据从宿主会话记录读：Claude 用每条记录的 `message.usage`，Codex 用 `token_count` 事件。在 `build_site --summary` 里显示。
  2. 预警阈值写进配置，例如 `budget.token_alert` 和每个角色的上限，处理方式与 `alert_node_h` 相同：只停止新增工作，不中断正在运行的作业。
  3. 轮换规则：worker 的上下文达到窗口的 X%，或者到达任务边界时，Leader 用 `resume_package` 开一个同身份的新会话（RULES:32 已经支持"接手会话"）。不等它被动压缩。
  4. 评审简报除了给路径，还要写明差异范围和要核对的不变量，以限制评审读入的内容。
- **代价**：低到中等。注意：轮换能否省 token 需要实测。本次没有对照，属于推断。

### 建议 3：预授权的模型和宿主替补顺序
- **问题**：模型或额度不可用时只能 BLOCKED。
  - 阶段评审因 Fable 不可用全部 BLOCKED（AGENTS-README:18-19）。
  - S1 运行因与实施会话共用的账户额度用完而中断（STATUS:117-118）。
  - research-agent 刻意不悄悄替换模型（RULES:42-48）。这个立场是对的，但没有提供经授权的替补方案。
- **LoopLora 的证据**：用户事先定了规则：Codex 周额度低于 20% 时，等当前工作结束，交给 Sonnet 子代理并关闭 Codex。执行时没有丢失工作。
- **建议**：
  - 在配置中增加 `models.<role>.fallback: [...]` 和 `fallback_when: {quota_below: 0.2, unavailable: true}`，`config apply` 时需要用户原话授权。
  - 发生替换时记录"请求的模型、观察到的模型、替换理由"，沿用 RULES:42 的三层模型证据。
  - 评审的替补也必须满足 `require_cross_family`。
- **代价**：低。

### 建议 4：预注册写明"结果区间对应的下一步"，并支持研究线级止损
- **问题**：
  - 节点结论只有三态（正、负、不确定），由 `minimum_practical_gain` 决定（RULES:157）。
  - 没有"某个结果区间触发哪项研究、关闭哪条线"的预登记。
  - 处置是逐节点的；停滞计数和失败预算按批次或根因计。
- **LoopLora 的证据**：
  - LSQT 的三个区间（触发 W3、开放、证伪并关闭）让结果一出来就能机械决定下一步。
  - U 对照组写成条件对照（最好的臂 ≥ 40% 才跑），没有为一个无法回答的问题花算力。
  - 学习式写入器线按登记规则停止，重开需要用户批准并重新预注册。
- **建议**：
  1. 在 `screening_contract` 中加入 `outcome_bands: [{range, consequence: trigger|open|close, target}]`。
  2. 加入 `conditional_controls: [{condition, design}]`。
  3. 每个"开放"区间必须带 `default_action`，避免研究线无限期挂着。这是 LoopLora 自己的教训。
  4. 引入"研究线"（line）分组：线级的止损、重开需要用户原话。ARIS 计划中 Scientist 的 `rule_ref` 机制（ARIS:184-235）可以直接承载这些规则。
- **代价**：中等，要动 schema。

### 建议 5：正式运行前的发布门
- **问题**：
  - research-agent 有 sanity 和不可变的 `method_spec`，但 walltime 和步数不属于方法身份（RULES:123）。
  - 没有"按冒烟实测冻结调度"和"重载一致性检查"这一步。
- **LoopLora 的证据**：
  - 每个正式运行前都有：发布文件冻结步数、评测点和 walltime（实测 × 1.5，按 2 h 上限反推步数），记录配置哈希和预注册摘要；然后做重载检查，最后提交批准记录。
  - 冒烟只读计时和显存，不读分数，发布文件里标 `quality_scores_exposed: false`。
  - 这样没有出现跑到 walltime 被杀、或者正式运行和冒烟配置不一致的情况。
- **建议**：新增 `release_schedule(experiment, smoke_run_ids)`。
  - 它从 sanity 运行的计时算出步数和 walltime，冻结后供 `reserve_submission` 使用。
  - 它运行一次"重载后预测一致"检查。
  - 记录必须写明分数没有暴露。
  - 批准由 Leader 登记。
- **代价**：中等。

### 建议 6：worker 粒度，允许"领域 worker"连续承接多个节点
- **问题**：每个假说节点绑定一个 worker（RULES:25；TSX:1477-1495）。每个新 worker 都要从约 3 万 token 起步，重新读一遍代码库。
- **LoopLora 的证据**：
  - sn-llm 连续做了 WP-L5、L7、L8、L12 四个工作包，包含多项研究，积累的代码知识可以复用。
  - 从 G5 批准（13:08）到 SQ2 和 LSQT 的代码、测试和发布完成（14:12–14:18），只用了约 70 分钟。
  - 代价是上下文很大，sn-llm 压缩了 11 次。
- **建议**：
  - 允许 Leader 把同一谱系（`variant_of`、`repairs`）的后继节点交给同一个 worker 身份接续。
  - 节点级的身份和审计不变，DB 记录"由 worker X 接续"。
  - 配合建议 2 的轮换规则使用。
- **代价**：低到中等。需要量化"重新读代码"和"带着大上下文"哪个更贵，可以用建议 2 的计量来测。

### 建议 7：结构化的等待和停止行协议
- **问题**：research-agent 的等待规则很完整（RULES:196-205），但没有规定 worker 交回时用什么固定格式。
- **LoopLora 的证据**：worker 的最后一行是 `WAIT <作业号> | <下一步>` 或 `STOP: <原因>`，编排者据此机械地布置监视任务或做决定，不需要读长文。
- **建议**：在 `message.schema.json` 中增加 `wait` 和 `stop` 两种类型，字段分别为 `job_ids`、`next`、`reason`。由插件自动布置监视任务（按 RULES:205 用宿主真实的机制），同一组作业只布置一个。
- **代价**：低。

### 建议 8：正式计算前的一次性静态评审（按代码路径，不按每次运行）
- **问题**：廉价筛选不做逐次代码评审（RULES:124）。代码缺陷要等到确认或候选阶段才会被评审发现。
- **LoopLora 的证据**：
  - 计算前的只读评审发现过一个 Medium 级问题，以及一处会让冒烟门在 2–10% 情况下误触发的平局规则。
  - 每次评审约 0.08–0.57 亿 token，远比在 GPU 上跑出错误结果便宜。
  - 测试作业里出现了 33 个退出码 1，说明缺陷大多在测试阶段被发现，静态评审是第二道网。
- **建议**：
  - 新的 `method_spec` 代码路径第一次提交计算前，触发一次低成本评审。允许同模型族，记为 `kind: static_precompute`，不计入五维评审。
  - 同一方法身份的后续运行不再评审，保持筛选的速度优势。
- **代价**：低。

### 建议 9：合并后的全量测试门
- **问题**：分支生命周期记在 DB（DB:5505-5545），但合并后没有要求跑集成测试。
- **LoopLora 的证据**：每次合并后都在计算节点上对明确的提交哈希跑全量测试（2,676 → 2,957 项）。共享注册表的冲突（`CONFIRMATION_WINDOWS`）靠"逐条断言"化解，测试能直接暴露合并错误。
- **建议**：分支状态改为 `merged` 时，要求登记一条集成测试运行（提交哈希、通过数、退出码）。没有这条记录，`get_eligibility` 视为未满足。
- **代价**：低。

### 建议 10：项目级的"不可写的表述"清单
- **问题**：`CLAIM_EXCEEDS_EVAL_TYPE` 只拦"优于 SOTA"一类的措辞（DB:4463-4480）。`evidence.py` 只检查数字是否存在，不检查措辞的范围（`evidence.py:1-17`）。
- **LoopLora 的证据**：论文台账维护了"不可写的表述"清单（例如"ridge storage solves the read distortion""untying improves B8"）。审核中拦下了因果性的过度表述，以及对后续研究的错误称呼。
- **建议**：
  - 每个节点或研究线登记 `must_not_say` 短语和模式，`set_document_current` 时扫描。
  - 证据阶段与措辞绑定，例如 `candidate_ready` 阶段的文档不能出现 "confirmed" 或 "确认"。
- **代价**：低。

## 10. research-agent 中 LoopLora 应当借鉴的部分

只列一部分，因为本文重点是改进 research-agent：
- **持久的消息日志**：按角色写 JSONL，区分已发送、已接收、已落实。LoopLora 的事件日志在 scratchpad 里，应当提交进仓库。
- **结构化的状态存储**：`docs/workers.md` 的长表格单元应当改成结构化记录，文档里只留指针。
- **作业账本**：预留和结算，状态未知的作业不重新提交。LoopLora 目前靠 PBS 历史和报告里的成本表，没有在代码中对账。
- **评审申诉通道**：保留原始的阻断意见，绑定一次独立复核，由 Leader 裁决（RULES:126）。LoopLora 的评审意见全部由编排者直接采纳或驳回，没有留下复核记录。

## 11. 不建议照搬的部分

- **编排者审核一切**：LoopLora 的规模下可行，但它就是吞吐上限。research-agent 用规则加代码判定、Leader 只处理例外，这个方向更对。
- **在 scratchpad 里手写监视脚本和事件日志**：只适合单次会话。
- **单 seed 的验证集筛选**：这次是为了在每条线上做最便宜的判定，每份报告都写明了这个限制。不宜作为默认的证据标准。
